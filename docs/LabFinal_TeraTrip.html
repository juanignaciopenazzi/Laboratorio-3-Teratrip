Laboratorio Final — TeraTrip Intelligent Data & Analytics

Ingesta inteligente de documentos + agente conversacional sobre Athena

1. Objetivo

Construir una solución end-to-end que permita a TeraTrip incorporar nuevas reservas desde documentos y luego consultar el dataset analítico utilizando lenguaje natural.

El laboratorio reutiliza la tabla sábana curada del Laboratorio 2 y agrega dos capacidades:

  1. Procesamiento automático de nuevas reservas mediante Textract.
  2. Un agente de Amazon Bedrock AgentCore capaz de convertir preguntas en SQL, consultar Athena y analizar los resultados.

Está diseñado para completarse entre lunes y viernes, con acompañamiento de tutores e IA.

S3 EventBridge Step Functions Lambda Textract Glue Athena Bedrock AgentCore Knowledge Base

2. Punto de partida

Se asume que el Laboratorio 2 está completo y existe:

  • El bucket de TeraTrip.
  • La capa curated/booking_analytics/.
  • El archivo teratrip_booking_analytics.parquet.
  • La tabla correspondiente en Glue Data Catalog.
  • La tabla consultable desde Athena.
No reconstruir el pipeline anterior. El objetivo del laboratorio final es extenderlo.

4. Parte A — Ingesta inteligente de nuevas reservas

Documento de entrada

Utilizar un PDF o imagen de una sola página con una tabla de entre 5 y 10 nuevas reservas.

Se entregan 5 PDFs de ejemplo únicamente como referencia del tipo de documento esperado. Cada intern debe generar su propio documento de prueba, pudiendo agregar reservas para clientes ya existentes o incorporar nuevos clientes. No deben utilizar uno de los PDFs de ejemplo como archivo final de la demo.

Como mínimo debe contener:

CampoEjemplo
booking_idB9001
booking_date2026-08-25
customer_idC221
customer_nameAna Pérez
customer_countryArgentina
destination_cityMadrid
product_typepackage
statusconfirmed
total_amount1200
payment_amount1200
payment_statusapproved
payment_methodcredit_card

Procesamiento automático

  1. El documento se deposita en incoming-documents/.
  2. S3 genera un evento que EventBridge utiliza para iniciar una Step Function.
  3. Una Lambda invoca Textract para detectar texto y tablas.
  4. Una segunda Lambda transforma la respuesta de Textract al esquema esperado.
  5. Los registros normalizados se escriben en incoming-data/.
  6. La Step Function ejecuta el Glue Job que incorpora esos registros al dataset curado.
  7. Se valida en Athena que los nuevos booking_id estén disponibles.
Para mantener el alcance manejable, el formato del documento es conocido y de una sola página. No se busca construir un parser genérico para cualquier factura o documento.

5. Actualización de la tabla sábana

Los registros normalizados quedan disponibles en incoming-data/. A partir de allí, cada intern debe elegir Lambda o Glue para incorporarlos al dataset curado.

Opción A · Lambda

Adecuada para el bajo volumen del laboratorio y transformaciones simples. Puede leer el Parquet actual, incorporar las nuevas reservas, validar duplicados y volver a escribir la tabla sábana.

Opción B · Glue

Permite reutilizar el enfoque de Data Engineering visto en laboratorios anteriores y deja una solución más preparada para crecer en volumen o complejidad.

No hay una opción obligatoria: la elección debe estar fundamentada según volumen, complejidad, costo y escalabilidad.

Independientemente de la herramienta elegida, el proceso debe:

  • Leer los nuevos registros desde incoming-data/.
  • Normalizar los tipos necesarios.
  • Evitar duplicar un booking_id existente.
  • Generar los campos derivados requeridos por la tabla sábana.
  • Mantener una única fila por reserva.
  • Actualizar de forma controlada teratrip_booking_analytics.parquet.
El mismo documento no debe poder generar dos veces la misma reserva. La solución debe contemplar al menos una validación por booking_id.

6. Parte B — Knowledge Base del negocio

Crear una Managed Knowledge Base que le dé al agente el contexto necesario para interpretar correctamente el dataset y las preguntas de negocio.

Se recomienda incluir información sobre:

  • Diccionario de datos: columnas disponibles, tipos y significado.
  • Reglas de negocio: reservas confirmadas, cancelaciones, pagos y relaciones entre los datos.
  • Definición de métricas: revenue confirmado, tasa de cancelación, cobertura de pagos y otras métricas relevantes.
  • Contexto del dataset: qué representa la tabla sábana, su granularidad y principales casos de uso.

Cada intern debe decidir cómo organizar esa información y en qué formato compatible con la Knowledge Base. La decisión deberá ser fundamentada durante el walkthrough.

La Knowledge Base contiene conocimiento sobre el dataset y el negocio. Los registros de la tabla no deben cargarse en RAG: los datos estructurados se consultan mediante Athena.

7. Agente de Analytics

Crear un agente utilizando:

  • AgentCore Harness.
  • Claude Haiku 4.5 como modelo.
  • Gateway con autenticación IAM / SigV4.
  • Managed Knowledge Base como un target.
  • Lambda de Athena como segundo target.

Convenciones importantes

  • El nombre del Harness debe usar letras, números y _. No usar guiones.
  • Los targets del Gateway deben utilizar guiones y no guiones bajos.
  • El rol de ejecución del Gateway necesita explícitamente lambda:InvokeFunction sobre la Lambda.
  • No utilizar Cognito/JWT para este laboratorio. Utilizar IAM.
  • No implementar Guardrails como requisito del laboratorio.

8. Tool de Text-to-SQL

Crear una Lambda expuesta al agente como una herramienta:

execute_athena_query(sql_query)

El agente deberá:

  1. Interpretar la pregunta del usuario.
  2. Consultar la Knowledge Base cuando necesite entender columnas, métricas o reglas.
  3. Generar una consulta SQL.
  4. Enviar el SQL a la herramienta.
  5. Recibir el resultado de Athena.
  6. Responder en lenguaje natural.

Ejemplo

Usuario:
¿Cuál fue el destino con más revenue confirmado?

Agente:
SELECT destination_city,
       SUM(confirmed_revenue) AS revenue
FROM booking_analytics
GROUP BY destination_city
ORDER BY revenue DESC
LIMIT 1;

Athena:
Madrid | 42500

Agente:
Madrid fue el destino con mayor revenue confirmado,
con un total de 42.500.

Restricciones obligatorias

  • Permitir únicamente SELECT y WITH ... SELECT.
  • Bloquear INSERT, UPDATE, DELETE, DROP, CREATE, ALTER y operaciones similares.
  • Permitir consultas únicamente sobre la tabla del laboratorio.
  • Limitar la cantidad de filas retornadas.
  • Aplicar mínimo privilegio en IAM para Athena y S3.

9. Pruebas obligatorias

Prueba 1 — Analytics

  • ¿Cuál es el destino con mayor revenue confirmado?
  • ¿Cuántas reservas canceladas tenemos?
  • ¿Cuál es el revenue confirmado por tipo de producto?
  • ¿Qué país tiene más clientes?

Prueba 2 — Uso de conocimiento

Realizar una pregunta que requiera entender una regla del negocio o una métrica definida en la Knowledge Base.

Prueba 3 — Seguridad

Intentar que el agente ejecute una operación que modifique datos. La herramienta debe rechazarla.

Prueba 4 — End-to-end

  1. Consultar al agente cuántas reservas existen para un destino.
  2. Subir un nuevo documento con reservas para ese destino.
  3. Esperar que finalice el pipeline.
  4. Consultar nuevamente al agente.
  5. Validar que la respuesta contemple los nuevos registros.
Esta última prueba es el resultado principal esperado del laboratorio final.

10. Walkthrough y entregable

El único entregable documental será un documento breve que contenga:

  • Arquitectura implementada.
  • Problemas encontrados y cómo fueron resueltos.

El resto será presentado directamente en AWS mediante un walkthrough de la ejecución completa del pipeline, incluyendo la Parte A y la Parte B.

Durante el walkthrough se deberá demostrar:

  • Ingreso del documento en S3 y disparo automático del flujo.
  • Procesamiento con Textract y normalización de los registros.
  • Actualización de la tabla sábana mediante Lambda o Glue.
  • Validación de los nuevos registros en Athena.
  • Knowledge Base, Harness, Gateway y herramientas del agente.
  • Consulta en lenguaje natural, SQL generado, resultado de Athena y respuesta final.
  • Prueba end-to-end antes y después de incorporar nuevas reservas.

11. Preguntas para investigar

  1. ¿Qué cambiarían si en lugar de un PDF de una página recibieran PDFs de decenas o cientos de páginas?
  2. ¿Cómo evitarían procesar dos veces el mismo documento si S3 o el pipeline generaran más de un evento?
  3. ¿Cómo validarían automáticamente que la respuesta del agente coincide con los datos realmente devueltos por Athena?
  4. Si una respuesta del agente es incorrecta, ¿cómo determinarían si el problema estuvo en el RAG, en el SQL generado, en Athena o en los datos de origen?

12. Criterios de aprobación

  • Un archivo nuevo en S3 inicia automáticamente el flujo de procesamiento.
  • Textract extrae correctamente las reservas del documento.
  • Los registros se incorporan sin duplicar reservas existentes.
  • La tabla sábana se actualiza y Athena devuelve los nuevos registros.
  • La Knowledge Base contiene contexto del dataset y reglas de negocio.
  • El agente genera SQL válido y consulta Athena mediante una herramienta.
  • La Lambda rechaza operaciones SQL no permitidas.
  • La traza del agente permite identificar las herramientas utilizadas.
  • La prueba end-to-end refleja el cambio después de ingresar nuevas reservas.
  • Se aplican permisos IAM de mínimo privilegio.
